# EGG HATCH バックエンド

設計ドキュメント(`egg-hatch-db-design.md`)の「次にやるべきこと」を、上から順番に実装しています。

- ✅ 1. users / works / applications の最小構成
- ✅ 2. パスワードのハッシュ化とログイン機能
- ✅ 3. 選考画面・制作スペースの権限チェック
- ✅ 4. ファイルアップロード
- ✅ 5. work_roles / creator_profiles テーブルの追加

## 中身

| ファイル | 役割 |
|---|---|
| `models.py` | テーブル定義一式(`User` / `CreatorProfile` / `CreatorTag` / `Work` / `WorkRole` / `Application` / `TeamMember` / `File`) |
| `auth.py` | ログイン機能(`/register` `/login` `/logout` `/me`) |
| `works.py` | 作品・募集役割・応募・選考・制作スペースのルートと権限チェック |
| `files.py` | ファイルアップロード・ダウンロード |
| `profiles.py` | クリエイタープロフィールの閲覧・更新 |
| `app.py` | Flaskアプリの土台 |
| `init_db.py` | データベースを作り、プロトタイプと同じサンプルデータを入れる |
| `requirements.txt` | 必要なパッケージ一覧 |

## 使い方

```bash
pip install -r requirements.txt
python3 init_db.py
python3 app.py
```

## 今回の変更点(work_roles / creator_profiles)

### `work_roles`(募集したい役割)を独立したテーブルに

これまで `applications.role_name` に文字列でそのまま持たせていましたが、
「作品ごとに、今どんな役割を募集しているか」を管理できるよう、
`work_roles` テーブルを新設し、`applications.work_role_id` で参照する形に変更しました。

- `POST /works/<id>/roles`:発案者のみ、募集したい役割を追加できる
- `PATCH /works/<id>/roles/<role_id>`:発案者のみ、募集を締め切れる(`is_open: false`)
- 応募は `role_name`(文字列)ではなく `work_role_id`(その作品の実在する役割のID)を指定する方式に変更
- **採用が決まると、その役割は自動で募集終了になる**(同じ役割に複数採用してしまう事故を防ぐ)

### `creator_profiles` / `creator_tags`(クリエイタープロフィール)を追加

- `GET /users/<id>/profile`:誰でも見られる(「私の世界観」・得意分野・やりたい役割・ジャンル)
- `PUT /me/profile`:**自分のプロフィールだけ**を更新できる
- `PUT /me/tags`:**自分のタグだけ**をまとめて更新できる

🔒 **ここでのセキュリティのポイント**:更新系のエンドポイントは、
「誰のプロフィールを更新するか」をURLやリクエストボディから受け取らず、
必ず**ログイン中の本人(`current_user`)だけ**を対象にしています。
これにより、他人のIDを指定して勝手にプロフィールを書き換えるような
攻撃(IDOR)が構造的に起こり得ません。

## 動作確認で分かったこと

以下はすべて実際に自動テストで確認済みです。

- 発案者以外は役割を追加できない(403)
- 存在しない役割IDに応募しようとすると400ではじく
- 発案者が応募を「採用」にすると、**その役割は自動で `is_open: false` になる**
- 締め切られた役割に、別の人が応募しようとすると400ではじく(「現在募集していません」)
- 誰でも他人の公開プロフィールを閲覧できるが、**編集は本人しかできない**(未ログインは401)
- 他人がすでに使っているハンドル名(`@〜`)には変更できない(409)
- ファイルアップロード(前回実装分)と、新しい役割ベースの応募が組み合わさっても正しく動く

## 番外編 -リレー漫画-(本編とは別枠の機能)

本編とは別に、「番外編」として**リレー漫画**の機能を追加しました。
1人で完成させるのではなく、誰かが描いた続きを別の人がつないでいく仕組みです。
プロ・アマの区別なく、誰でも同じ条件で「続き」に応募できます。

**シーズン制(春夏秋冬)**:番外編は「シーズン」(約3か月・春/夏/秋/冬)単位で
運営が1つのテーマを発表し、そのテーマから参加者がリレー形式で短編漫画を
作っていく構成にしています。既存のパート・応募・採用の仕組み(`RelayManga` /
`RelayPart` / `RelaySubmission` / `RelayRecruitment`)はそのまま残し、その上に
`RelaySeason`(シーズン)を追加しただけです。

- `GET /relay/seasons/current` ― 現在開催中のシーズン(テーマ・開催期間・
  そのシーズンの作品一覧)。番外編トップの主役として表示されます。
- `GET /relay/seasons` ― 過去のシーズンも含めた一覧(アーカイブ)。
- `POST /relay/seasons`(運営のみ)― 新しいシーズンを開始する。開催中の
  シーズンがあれば自動的に「終了(ended)」にしてから切り替わります。
- 各リレー作品には `stage_label`(例:「アイデア段階」「作画募集中」
  「制作中」「完成」など)という自由記述の進行状況ラベルを追加しました。
  工程を固定のパイプラインにはせず、運営が `PATCH /relay/mangas/<id>` で
  随時アップデートする想定です。
- 新しいリレー作品を作成する際に `season_id` を指定しなければ、自動で
  現在開催中のシーズンに紐づきます。

**企画としての位置づけ**:「続きを競うコンテスト」ではなく、「みんなで一本の漫画を
つないでいく公式リレー企画」として見せています。運営が1作品を選ぶ操作も、
「勝者を決める」「審査で優劣をつける」ではなく「今回の公式の続きとして採用する」
「次につながる作品を決定する」という位置づけで文言を統一しています。採用され
なかった作品も「落選」ではなく「今回は公式ルートには含まれなかった」という
扱いです(データ上のステータス名は `accepted` / `rejected` のままで、変えている
のは画面に表示する文言のみです)。

- トップページ下部、または `egg-hatch-relay.html` からアクセスできます
- 番外編の画面からは、いつでも「EGG HATCH本編へ」のリンクで本編に戻れます
- 認証・プロフィール・安全なファイルアップロードは、本編の仕組みをそのまま再利用しています
  (番外編専用の重複した仕組みは作っていません)
- 本編の既存コード(`works.py`・既存モデル・既存の7画面)は変更していません
  (`User`に`is_admin`列を追加した点のみ、本編にも影響する変更です)

**画面構成**:
- `egg-hatch-relay.html` ― 番外編トップ(現在進行中のリレー漫画一覧)
- `egg-hatch-relay-detail.html` ― リレー漫画詳細(採用済みパートを順番に閲覧)
- `egg-hatch-relay-submit.html` ― 続き応募画面
- `egg-hatch-relay-review.html` ― 公式ルートを決める画面(運営専用。`is_admin`のユーザーのみ)
- `egg-hatch-relay-admin.html` ― 番外編 管理画面(運営専用):
  ①新しいシーズンを作る　②テーマと期間を編集する　③作品を作る　④進行状況(`stage_label`)を変更する
  ―の4つをこの1画面から行えます。番外編トップに運営としてログインすると
  リンクが表示されます。

**お試し用**:`tachibana@example.com`が運営(`is_admin=True`)としてログインでき、
この画面から届いた続きを確認し、今回の公式の続きとして採用する・次の募集を開始する、
といった操作ができます。サンプルのリレー漫画
「夜明けの町」(パート1公開済み・パート2募集中・紙谷さんからの応募1件)が
最初から入っています。

**まだ実装していない部分**(仕様書の「まず基本機能が成立するところまで」を優先):
- 募集の締切に到達しても自動では閉じません(採用操作で手動的に閉じる想定です)
- シーズンの開催期間(`ends_at`)が過ぎても自動では終了しません(運営が次のシーズンを
  開始した時点で、自動的に前のシーズンが `ended` になる仕組みです)
- 1回の応募の複数ページ・複数ファイル対応(現状は1応募＝1ファイル)
- 運営が既存の募集を取り消す(締切前に閉じる)UI

## フロントエンドとの接続について

このバックエンドは、これまでプロトタイプとして作っていたフロントエンド
(`../templates/` `../static/`)と接続済みです。

- `pages.py` が、これまでのHTML画面(`egg-hatch.html` など)をそのまま配信します
- 各画面のJavaScript(`static/js/egg-hatch*.js`)は、サンプルデータ(SAMPLE_*)ではなく
  実際にこのバックエンドのAPIを呼び出すように書き換えました
- ログイン・新規登録の画面(`egg-hatch-login.html`)を新規に追加しました
  (これまではAPIしか無く、ブラウザからログインする画面が無かったため)

起動方法は変わりません。`python3 app.py` を実行し、ブラウザで
`http://127.0.0.1:5000/` を開けば、そのままフロントエンドが表示されます。

### つながっていない・簡略化されている部分

- キャラクター設定：まだ専用のテーブルが無いため、作品詳細ページには表示されません
- 制作進捗(%)：正確な値を管理する仕組みが無いため、「募集役割が埋まった割合」で代用しています
- プロフィールの「過去の提出作品／参加作品／完成作品」：まとめて取得するAPIがまだ無いため、準備中の表示にしています
- 制作スペースのチャット・ラフ提出・ファイル共有一覧：まだ専用のテーブルが無いため、
  画面を開いている間だけの一時的な機能のままです(ファイルのアップロード自体は本物のAPIを使っています)
